# Install, update and the container image

Covers `install.sh`, `run.sh`, `updates.py` and the `Dockerfile`.

## Settings

**Settings are runtime, flags are launch-only.** Everything the admin offers - the detector's address and password included - lives in `--config` (default `detector/data/settings.json`), so a frame is re-pointed without a restart.

**The environment seeds settings; it never overrides them** (`settings.from_env`). `FUGLERAMME_<FIELD>` for any field of `Settings` but `session_secret`, read off the dataclass so a new setting needs nothing added. It exists for the container image, where a fresh `/data` has no `settings.json` and the detector's address has to come from somewhere. These become the store's *defaults*, exactly as `--detector` does: a key the file carries wins, so a variable goes quiet from the first Save on. Override-on-boot instead and the admin page - which offers to change every one of them - would be lying. Precedence is `settings.json` > `--detector` > environment > built-in default. `--detector` is only ever BirdNET-Go's address, as `run.sh` bakes it; a container seeds stations through `FUGLERAMME_DETECTOR_KIND` and `FUGLERAMME_DETECTOR_STATION`, several separated by commas. `FUGLERAMME_DETECTOR_TIMEOUT`, `FUGLERAMME_LOG_LEVEL` and `FUGLERAMME_BASE_PATH` are not settings: never seeded into `settings.json` or offered by the admin. On a Pi they go in a `systemctl edit` drop-in, which updates and `run.sh` leave alone.

## The install splits at the reboot (`install.sh`, `run.sh`)

- `install.sh` is the curl'able one-time bootstrap: deps, clone, groups, SPI/I2C overlays, gadget mode. Everything in it only takes effect on boot, so it is the only script that prompts a reboot - and only if something actually changed. It must stay self-contained; it is fetched before the checkout exists.
- **`install.sh` checks out the latest release tag, not `main`** (`FUGLERAMME_REF` overrides). Releases are cut by hand, so `main` can carry work no Pi has been given. The script itself is curled from `main`, though, so it runs against the last release's `run.sh`: anything new it needs from `run.sh` has to ship before it is used.
- `install.sh` also asks where BirdNET-Go lives: installed here, already running on this machine, or on another. The answer plus the two ports land in a gitignored `frame.env` at the repo root, which `run.sh` sources. Only a bundled detector gets a `detector/.env`, so an external install skips the container everywhere by that one marker. A BirdWeather station is set on the admin page, not here (#263).
- `run.sh` is the idempotent converge: `uv sync`, config, compose up, systemd unit. Re-run after a pull or a repo move - it bakes `$REPO_ROOT`, the frame's port and the detector's URL into the unit.
- **An update cannot install `libfribidi0`.** Pillow's wheel loads it at runtime for raqm, which shapes Arabic, Hebrew and Malayalam labels. `run.sh` installs it (`install.sh` ends by running it) and the image carries it. A frame installed before v0.28.0 draws those names as scientific ones until it is installed by hand; the admin says so under the language selects, with the command.
- **`updates.apply` never re-runs `run.sh`.** A Pi that auto-updates keeps its old unit, its old `detector/.env` and its old `settings.json`, so every default a release introduces must reproduce the previous one's behaviour: frame on 8080, bundled detector on 8090, `detector_url` of `http://127.0.0.1:8090`, `detector_kind` of `birdnet-go`. A new compose variable needs its default inline (`${BIRDNET_PORT:-8090}`), not only in `frame.env`. Get this wrong and working appliances break on update, which is the one failure nobody can recover from remotely.
- Machine-specific values are detected or prompted for and written to gitignored per-Pi files (`frame.env`, `detector/.env`), never hardcoded in tracked defaults. `updates.apply` checks out with `--force`, so committing a currently-ignored per-Pi path puts it in the blast radius.
- The self-update converges the detector too, so a release can move the image pin (`updates._converge_detector`). It is `up -d`, not run.sh's `--force-recreate`: an unchanged pin must not bounce a working detector. `detector/.env` is the marker for "an appliance, not a dev checkout", and a failure only logs - the frame is already on the new version by then. The DB is copied to `birdnet.db.bak` first and a failed copy skips the swap, since the new container migrates it in place on first start. Upstream tags by date and the pin reaches every frame, so test a bump on the Pi before tagging the release that carries it.
- With a reboot pending, `--no-start` leaves the frame enabled but stopped, since there is no SPI and no group membership yet. The container starts either way: `restart: unless-stopped` only revives a container that was already running.
- Prompts read `/dev/tty`, not stdin - under `curl | bash` stdin is the script itself. Same reason the body is wrapped in `main`, called on the last line.
- BirdNET-Go must run with the host user's UID and GID so its mounted config and data remain writable without changing checkout ownership.
- USB gadget access is documented in troubleshooting; do not assume `10.12.194.1` when macOS Internet Sharing may assign a leased address.

## Gift mode (`gift.py`, #355)

- The last step on a frame that already works: install, test the panel and the mic, then wrap it. A one-off tool beside the product, not a part of it, so it stays small. It is a CLI, never the admin: wiping the history and forgetting the Wi-Fi do not belong on a page that may have no password.
- Any frame with an Inky can be wrapped. One that reads BirdWeather, or a BirdNET-Go elsewhere (no `detector/.env`, or `detector_kind` BirdWeather), has no place or history of its own: it is warned at the start, and the wrap leaves BirdNET-Go alone and never asks about deleting.
- **The frame service knows nothing of it.** The CLI borrows the frame: it stops `fugleramme-frame`, drives the panel itself, and starts the service again on any exit but a wrap. A wrap powers the Pi off with the splash on the glass; the unit is still enabled, so the next boot, the recipient's, is an ordinary frame. The splash lives in the box only. Keep it so: a gift feature in the render loop has to freeze buttons, updates and the setup screen, and every state it adds is a way to strand a frame.
- The questions are `giftform.py`, apart from `gift.py`: prompt_toolkit's one-line `prompt`, one question at a time, each asked again until it is right. The birds, and the timezone when it has to be asked, are searched as they are typed, over the whole line because a name has spaces. `prompt`, not a `PromptSession`: a session keeps one question's search for the next. A note line is checked against the attached Inky's real size, turned by the frame's rotation. The title shrinks to fit that width, down to the note's size, as a portrait panel is too narrow for the one offered.
- The splash is drawn after the last question and after every change, and waited for, so what is wrapped is the picture on the glass, and a refresh is never cut short. Every bird is the collage's own size: no spotlight, whatever the frame's setting.
- Its birds are the ones the giver names, or else the most recorded near the place that the style has a plate for: `BIRDS` of them unless the giver asks for another number. Either way at most `MOST_BIRDS`. "Most recorded" is GBIF's, asked live for `NEAR_KM` round the place in the current month of the last ten years, as `tools/species_map.py` asks of a country; when GBIF does not answer, the species page's own snapshot (`hooks/species_by_country.json`) gives the country's, all year. No BirdNET-Go is asked, so a frame on BirdWeather gets the same picture. Unheard birds only ever appear there, never as the page after it is opened (#347).
- The place is always set on a frame with its own BirdNET-Go, and the timezone whenever it is not the Pi's already; deleting the history (typed `delete`), forgetting the saved Wi-Fi and clearing the admin password are asked when the giver chooses to wrap. Everything the wrap will do is then listed, and it takes a typed `y` to go on: a no changes nothing and goes back to the summary, with the picture still on the glass. The recipient's own Wi-Fi is never saved: the setup screen is for that.
- **There is no undo**, and nothing is recorded for one: the Pi is off when a wrap ends, and a wrap that fails says which steps it had done. Running it again with another place is the way back.
- `restart: unless-stopped` never revives a container stopped by hand, so BirdNET-Go is brought back in a `finally`, whatever failed after the stop. `up -d`, not `start`: it recreates the container when its `TZ` changed. The history is deleted last of the steps that can fail, and the glob takes `updates._backup_db`'s `birdnet.db.bak` with it, or an auto-updated frame ships the giver's history.
- The timezone is Open-Meteo's for the place, as Photon gives none. It goes to the Pi (`timedatectl`) and to `TZ` in `detector/.env`, which nothing but `run.sh` writes. Left as the giver's, the page's dates and times are theirs and its day turns over at the wrong hour.
- Everything is on the card before the power-off is tried, so pulling the plug does the same. The Wi-Fi is forgotten after the last message is said and just before the power-off, as it may be the connection the giver is on; `sudo -v` runs before the steps so the power-off needs no prompt by then.
- Root is asked for in the terminal (`gift.root`), not added to `install.sh`'s rule: a rule only reaches frames that run the install again.
- `--preview OUT.png` asks the picture's questions and writes the splash to a file, with no service, panel or wrap: the way to work on the splash at a desk.
- The place is written into `config.yaml` by line, inside `birdnet:` only, to leave the rest as BirdNET-Go wrote it. The hostname and whatever was set in BirdNET-Go's own UI are left alone.

## Releases

- Cut by hand: `release.yml`'s `workflow_dispatch` runs python-semantic-release on `main` once its ci is green, bumping by the commit types since the last tag (`CONTRIBUTING.md`). Its `force` input bumps when only `chore` is queued.

## The image is the kiosk alone

`Dockerfile`, `.dockerignore`, `.github/workflows/image.yml`.

- Pull it, point it at a BirdNET-Go you already run, read the collage on a web page. No panel (SPI, I2C and the buttons are the Pi's) and `install.sh` knows nothing about it - both their own follow-ups, not gaps to fill in passing.
- `examples/docker-compose.yml` is what brings a detector up beside it, for a machine with a mic and no panel. It is documentation, curl'able straight from `main`, so it pins the same BirdNET-Go tag `detector/docker-compose.yml` does - `tests/test_container.py` holds the two together, since the pin only moves after it is tested on the Pi.
- **The checkout's shape has to survive into the image.** `config.REPO_ROOT` is derived from the package's own file, and the artwork, the fonts, the labels and `bird_sizes.csv` all hang off it, so the project is installed editable at `/app` with `/app/src/fugleramme` beside `/app/assets`. A build-time `RUN python -c` asserts it: fail the build, not the first render.
- The plates are split across a COPY layer per letter range so a release adding a species re-pulls that range instead of all 165 MB - the registry serves blobs by digest, so the letters that did not move are already on disk. The ranges must leave no letter out, and a range matching nothing fails the build; `tests/test_container.py` reads the globs back out of the Dockerfile and holds them to both.
- Everything mutable already derives from `--config`'s parent, so one volume at `/data` is the whole persistence story and no code knows about it.
- **The admin reboots only the Pi's service** (`updates.can_reboot`): systemd's `INVOCATION_ID` and no container. A dev run would reboot the workstation and an image's host is its own. It is `sudo -n systemctl reboot`, which the first user on Raspberry Pi OS images before 2026-04-13 may run without a password, and `install.sh`'s sudoers rule (`ensure_sudoers`) allows wherever the install has run since; anyone else gets sudo's refusal on the System tab.
- **A failed update puts the checkout back.** `apply` records `HEAD` first; if the new tag's dependencies do not install, it checks that commit out again before raising, so a restart never runs the new code on the old environment. `update_error` still stops further automatic tries until the admin retries.
- **`updates.apply` refuses in a container** (`updates.in_container`, the image's own `FUGLERAMME_CONTAINER`): there is no checkout to move onto a tag, no systemd to restart it, and handing the frame the docker socket buys a button. `available()` still runs - knowing a release is out is the half that works - and the admin drops the Install button, shows the auto-update toggle disabled, and prints `updates.CONTAINER_COMMAND` in its place. An install that sets `FUGLERAMME_CONTAINER` without being the image (the community Proxmox LXC) names its own command in `FUGLERAMME_UPDATE_COMMAND` (`updates.update_command`). Like `FUGLERAMME_LOG_LEVEL` it is launch-only, not a setting: how the frame was installed is not the admin's to change. The admin shows that command on every screen, without the link to the container docs.
- **The panel half stays on systemd + git, not in an image.** A git update ships about 2.5 MB to a Pi on wifi; pulling a new image ships the whole artwork tree, near 1 GB, and layer ordering does not help because the assets layer is the one that keeps changing. The letter-range COPY layers above are what make that bearable for the kiosk image, where the machine is on ethernet.
- `image.yml` is a separate workflow from `release.yml`, which dispatches it for the tag it cuts - a tag pushed with `GITHUB_TOKEN` starts no workflow, so `image.yml`'s own tag trigger only fires for a tag pushed by hand. The release's job is to cut the tag; a slow or broken image build must never delay or fail a version bump. Native runners per architecture, pushed by digest, with a merge job for the manifest list.
